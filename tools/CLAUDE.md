# tools/ (guidance for Claude)

Each entry: what the tool is, and where its feedback lives (artifact db collections and doc ids). Read the relevant artifact db before working on a review; see the root `CLAUDE.md` for the rules on feedback.

- `tools/segments/`: one working document per campaign segment, as an artifact. Each folder has a shared-layout `index.html` and its content in `segment.js`; see `tools/segments/README.md`. `01-opening/` is the opening, beats 1 to 7, and is where those beats are kept. Marks are in its db collection `ratings` (`map-*`, `job-*`; a job is bought only when marked `approve`). Notes are per round (the round is `round:` in `segment.js`, currently 5, so `r5-*`) in `answers` and `ratings`. Concepts (`concepts` in `segment.js`) are marked `concept-<id>` in `ratings` ({mark: go/rework/wrong}) with notes `r5-concept-<id>`, and their questions answered as `r5-<question id>` in `answers`: `weapons` (`weapons-focus`, `weapons-open`, `weapons-briefing`, 2026-11-22) and `walks` (`walks-fights`); the archived `academy` concept's ids were `academy-court`, `academy-route`, `academy-build` (never answered). The `board` at the top (stop × stage) is the segment's status; update it with any change to the segment.

- `tools/kit/`: the modular kit on a square grid (`docs/explorations/2026-11-23-flexible-building.md`; its `README.md` has the scene format). `kit.json` is the asset contract (each piece's box and pivot), `scenes/*.scene.json` are the scenes (a terrace per grid corner, plus flights, curves, edge overrides and vignettes; the old `layouts/*.py` are kept as history), `compile.py` turns a scene into piece instances and findings (`python tools/kit/compile.py patch-b`, written to `game/packages/client/src/lab/kit-<name>.json` for the greybox page `kit3d.html`), `scene.py` converts and checks, `worker.py` compiles for the map editor, `tess_layout.py` lays road and paving stone by stone for the floor shader (run by `compile.py`, and by `stones_worker.py` in the map editor after each edit), and `fit.py` (Blender) fits a Meshy model to its piece. No db.
- `tools/map-editor/`: the 3D map editor the user and Claude share (`docs/explorations/2026-11-23-map-editor.md`; README has the API and the controls). The page is `game/packages/client/editor.html` on the dev server; its scene server is the Vite plugin in `game/packages/client/map-editor/`. Claude works through `cli.mjs` (get, query, apply, undo, pins, view; edits land in a draft, and `save` / `discard` are the user's to ask for); `hook.mjs` (a `UserPromptSubmit` hook in `.claude/settings.json`) brings new pins into the session. Feedback lives in the pins (`tools/kit/scenes/<name>.pins.json`), not an artifact db: resolve each with an outcome (scene, rule or piece). A scene's concept images are in `tools/kit/scenes/refs/<name>/` (listed in `<name>.refs.json`); a pin on one has `anchor.ref`, and `cli.mjs ref <name> show <id> --pin <pin>` draws it for you to look at.

- `tools/prune-worktrees.mjs`: removes finished worktrees (clean, merged into another branch, idle 24h, not open in a running process; Claude Code's own `claude session ... (pid N)` pin lapses when that pid ends). Dry run by default, `--apply` to act, `--detach` is the SessionStart hook in `.claude/settings.json` (log in `.claude/worktree-prune.log`). Lists `UNMERGED` worktrees and orphan folders with files not in git, and never touches them. Before deleting a folder it removes every symlink and junction in it on its own (never what they point at), because git and rm follow a Windows junction while deleting: a `node_modules` junctioned to another worktree's once emptied court-kit's `game/packages` (2026-11-25). So don't junction `node_modules` across worktrees; run `npm install` in each. The rules for where sessions work are in the root `CLAUDE.md`.
