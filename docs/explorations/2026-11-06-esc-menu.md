# The Esc menu (2026-11-06)

The user asked for an Esc menu to start some navigation: a place to connect for multiplayer, and a way to travel between "scenarios" (the tutorial, the sandbox, Survive and so on). The scenario list will be redesigned closer to a beta. For now it only needs to move you between the rooms. This is what was built and why, plus the open questions.

## What it feels like

- **Esc is still "clear the queue" first.** With runes queued, Esc refunds them as it always did. With an empty queue, Esc opens the menu. Esc in the menu closes it. A player mid-spell never loses a fight to a menu popping up, and from anywhere two presses reach the menu.
- **On a gamepad, Start (Options) opens and closes it.** Back still clears the queue. In the menu, the D-pad or left stick moves, A selects and B goes back.
- **Offline, the world stops.** Enemies, spells and the clock freeze behind the menu. The header says PAUSED.
- **Online, the world can't stop.** The header says "ONLINE - THE GAME KEEPS RUNNING". The Resume page adds that your wizard stands still while the menu is open: the keyboard is released when it opens, so you don't keep walking or channelling. Your partner sees you stand there.

## Layout

The menu is drawn like the rune HUD: art pixels in a small canvas, the HUD's 3x5 font, its dark panel colours and gold highlights, at the HUD's automatic integer scale. At 1280 x 800 that scale is 2x. A small screen (640 x 400) gets 1x, which is small but crisp, the same size as the HUD there. A forced `?scale` doesn't blow the menu up past the screen.

```
+--------------------------------------------------------------+
| WIZARD SIM                                           PAUSED  |
+--------------+-----------------------------------------------+
| RESUME       |  TUTORIAL                        COMING SOON  |
|>SCENARIOS    |   Learn the runes, the casts and your hands... |
| MULTIPLAYER  |  SANCTUM (1)                  HERE - RESTART  |
| CONTROLS     |   The sandbox: three practice dummies...      |
| SETTINGS     |  ARENA (2) ...                                |
|              |  SURVIVE (3) ...                              |
+--------------+-----------------------------------------------+
| ARROWS / WASD MOVE - ENTER SELECT - BACKSPACE BACK - ESC ... |
+--------------------------------------------------------------+
```

Tabs sit on the left and the open section on the right. Up and down move along the column you're in. Right or Enter steps into a section, and Left or Backspace steps back out. Greyed items are skipped. The mouse hovers and clicks, and a click beside the panel closes it.

## What each item does

- **Resume:** closes the menu. It also says whether the world is paused or still running.
- **Scenarios:** one row per entry in `game/packages/client/src/scenarios.ts`, each with its name, number key and one-line description.
  - The current one is marked HERE, and picking it restarts it.
  - Offline, a switch rebuilds the world in place, without a reload. Seated gamepad players stay, an open lobby stays open (and now announces the new room), and the URL anchor follows so a reload brings you back.
  - The number keys 1 / 2 / 3 use the same registry and the same switch, but only out of an online match, where one stray key would move everyone.
  - **Online, only the host switches, and everyone follows.** The netcode had no room switch, so one was added in `netplay.ts`. The host starts a new match with everyone still playing, in the same seat order, in the new room. The start message names the old match (`prev`), so the other pages follow it by themselves, with no lobby round trip. Everyone else sees the rows greyed with HOST ONLY. A joiner still waiting in a lobby sees "The host picks the scenario".
  - **The tutorial** has its row now, greyed as COMING SOON. It turns on by itself once the sim has a `tutorial` room. The registry checks `ROOM_DIMS`, so adding the room is the whole change.
- **Multiplayer:** the same lobby as the Co-op panel (bottom left), drawn as menu items. The netcode wasn't touched beyond the room switch. What it shows depends on where you are:
  - On the hosted page, over WebRTC: **Host a room** (opens a four-letter code) and **Join by code** (type the four letters straight into the field, then Enter).
  - With `?net=bc`, or in the artifact's room: Host a match, and the list of open matches to Join or Rejoin.
  - While hosting: the room code in large gold letters, who has joined (P1 YOU, P2 HERE), **Start the match** and Cancel.
  - In a match: the code, your seat (and whether you're the host), the round trip, every seat's status (here, not responding, gone) and **Leave the match**.
  - Starting a match, or being moved by the host, closes the menu.
- **Controls:** a static reference in two columns, taken from `docs/current-state.md` and `gamepad.ts`. It covers runes, casting with runes queued, your hands with nothing queued, the gamepad, and the other keys (1 2 3, F1 tuning, F2 help, Alt inspect, backquote debug).
- **Settings:** **Pixel scale** (Auto, 1x to 4x), **Lights** (on or off) and **Debug line** (on or off). Each one mirrors its URL param (`?scale`, `?lights=0`, `?debug=0`) and writes it back into the address bar, so a reload keeps it. There's no volume setting, because the game has no audio yet.

## Trade-offs, named

- **Esc does two jobs.** A player who wants the menu with runes queued has to press Esc twice. The alternative, a separate menu key, means one more key to learn and loses the convention every PC game uses. Esc-clears-first protects the spell, and that matters more.
- **Pausing is offline only.** A paused co-op match would need everyone's agreement. That's a design question (see below), not a netcode one.
- **Moving the match makes a new match.** That's simple and reuses the start path, so no new protocol state was needed. But a player who had dropped (a gone seat) isn't carried over. They can't rejoin the new match, because it has no empty seat to announce.
- **Gamepads can open, move and select, but can't type a room code.** Joining by code from the couch needs the keyboard. The bc and artifact lists, which need no code, work fine with a pad.
- **The Co-op panel stays** in the corner. The network e2e test drives it, and it's a quick glance at the connection. It and the menu show the same lobby.

## Open questions

1. **Should the host pausing pause everyone online?** Magicka doesn't pause online. A "host pause" would freeze the match for everyone (the sim would stop on an input everyone agrees on). It's useful for a couch-and-voice group and annoying with strangers. The default for now: no pause online.
2. **Should a scenario switch online ask first?** Right now the host's pick moves everyone at once (a message says who moved it). A "Host wants to go to Survive" prompt is safer with strangers, but slower with friends.
3. **Should the Co-op panel go,** now that the menu has the lobby? My recommendation: hide it behind the menu once the e2e test drives the menu instead.
4. **Where does the tutorial sit?** It's first in the list, since that's the natural order for a new player. Its number key is 4, so 1 / 2 / 3 keep their meaning.
5. **Should the number keys be dev-only?** They switch the scenario with one press. Built: they work offline and do nothing in an online match, where the host uses the menu. Another option is to drop them once the menu is familiar.

Code: `game/packages/client/src/menu.ts` (drawing, input), `menu-nav.ts` (the Esc rule, focus movement, gamepad mapping, all pure and tested in `test/menu.test.ts`), `scenarios.ts` (the registry) and `net/netplay.ts` (`switchRoom`, `lobbyView`). `node scripts/menu-check.mjs` checks the menu in headless Chrome (Esc opens, pauses, clears and closes; hosting and switching from the keyboard) and takes the screenshots.
